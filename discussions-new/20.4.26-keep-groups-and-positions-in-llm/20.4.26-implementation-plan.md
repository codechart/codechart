# Implementation Plan: Keep Groups & Positions in LLM

## Goal
Import and export diagrams to/from LLM with full fidelity:
- Node positions (x, y) preserved
- Group nodes and their boundary nodes included
- Remark nodes included
- Claude preserves all of the above when updating a chart

---

## Files to Modify
- `packages/ui/src/app/search/llmJson.actions.ts`
- `packages/ui/src/app/search/llmJson.prompts.ts`

---

## Step 1 — Extend `LlmJsonItem` interface
Add optional fields to the existing interface:
```typescript
x?: number
y?: number
belongsToGroup?: number  // incremental ID of the paired group node
```

---

## Step 2 — Fix `isNodeExcludedForLlm()` (line 205)
Remove exclusions for `boundaryNode` and `groupNode`.
New logic: only exclude `isFilenameNode` and `isFileNode` (raw file containers).
> Note: verify `isFileNode` doesn't catch groupNode — groupNode is created via `createFileNode()` so may need `&& !isGroupNode(node)` guard.

---

## Step 3 — Update `mapForLlmJson()` export (line 214)
1. **Positions**: for every node call `this.chartWrapper.getPosition(node.id)` → include `x`, `y`
2. **Group nodes**: export with `type: 'group'`, label, content, position, `connectedTo: 0`
3. **Boundary nodes**: export with `type: 'boundaryNode'`, position, `connectedTo: 0`, and `belongsToGroup` mapped from original vis.js ID → incremental ID (using `savedIds`)

---

## Step 4 — Update `parseLlmJson()` validation (line 32)
Add a third validation branch alongside `todo` and CODE:
- `group`, `boundaryNode`, `remark` — do not require `filePath`/`lineContent`/`lineNumber`
- `boundaryNode` — requires `belongsToGroup` (number)

---

## Step 5 — Add private creation methods to `LlmJsonActions`
Three new methods (headless, no UI side-effects):
- `createGroupNodeForImport(label, content, x?, y?)` — creates group node only (no boundary)
- `createBoundaryNodeForImport(groupVisId, x?, y?)` — creates boundary with `belongsToGroup = groupVisId`
- `createRemarkNodeForImport(label, content, x?, y?)` — calls `chartActions.createShape()` with type `'remark'`

All must call `addFilesToLegend` to register the node.

---

## Step 6 — Update `processChild()` (line 166)
Add cases for `NodeTypes.groupNode`, `NodeTypes.boundaryNode`, `NodeTypes.remarkNode` using the new methods from Step 5.

---

## Step 7 — Update `processAllItems()` (line 178)
After creating all nodes:
1. Keep a parallel map `Map<number, VisiNode>` (incremental ID → vis node)
2. **Second pass** over all items:
   - If item has `x`/`y` → call `chartWrapper.setNodePosition(node, {x, y}, true)`
   - If item is `boundaryNode` with `belongsToGroup` → resolve incremental ID → actual vis.js ID, set `node.d.belongsToGroup = actualVisId`
3. Skip `positionNonMatchNodes` for nodes that already have explicit positions

---

## Step 8 — Update `llmJson.prompts.ts`
- Add `x`, `y` (optional numbers) and `belongsToGroup` (optional incremental ID) to both schema definitions
- Document `type: 'group'`, `type: 'boundaryNode'`, `type: 'remark'` as valid node types
- Add instruction: *"When updating a chart, preserve all x/y positions and group/boundary/remark nodes unless explicitly asked to change them."*

---

## Risk / Watch Points
1. `isFileNode()` may catch groupNode (both created via `createFileNode`) — verify exclusion logic
2. `createGroupNode()` in AppComponent calls `addFilesToLegend` + positions — import path must replicate this
3. `expandConnectedTo` pre-processing may duplicate group/boundary nodes if they have array `connectedTo` — verify
4. Boundary node IDs in export use vis.js internal string IDs — ensure incremental ID mapping covers them

---
